## 1. 把下一步说准

联合决定保留支持、采用什么证明、何时补取或重算，是正确的研究对象。但下一轮
首先追问：**原生操作改变了什么行为义务，允许读取的支持结构能否计算这些变化，
并直接构造合法的表示与证书更新？** 成本策略应调用这个底层构造，不能取代它。

继续承接 BRFP → OCAR。母问题仍是有限资源下维护表示对后续操作的充分性；
共同任务、相同信息权限及完整成本用于检验实际增量。现象、理论、方法各有独立
创新仍是尽量达到的目标，不能把最低 gate 当作研究上限，也不能预先宣布达成。

本轮已有的证明代换被通用 dependency-DAG 控制完整追平。因此，把 `Retain /
Acquire / Recompute` 列为动作，或者给它们增加一个调度器，还没有拿出独立算法。
下一步必须找出能够计算、具有成立边界、且强对照没有便宜解决的结构性障碍。

## 2. 必须区分的四件事

1. **事实变化**：原生状态、实体、版本或权限真的改变了。原生解释器决定其含义。
2. **行为义务变化**：剩余操作与观察契约改变了需要保证的行为。
3. **物理支持变化**：维护器删除、保留或重建实际可执行的表示组件。
4. **证明变化**：旧证书失效，或换成另一套有效证书；事实和目标行为未必改变。

依赖索引只能说明当前证明用到了什么。**旧证明不能用了，不等于目标行为失效，
也不等于必须补取原事实。** 本轮六节点例正是：删除物理 b 后，旧 e 的 literal
证明悬空；通过 b 的替代路径可继续保证 e 对应的可达行为。

同样，证明“省略 b 不影响承诺的行为”不等于恢复 b 的来源真值、内容或身份。
证明节点不应被解码器冒充为已取得的原记录。来源内容、行为替代与实体身份的
要求须由原生任务分别定义。

## 3. 算子的输入、写入与失败含义

维护器的可见状态记为 `z=(r,C,S,Γ,index)`：实际表示、契约、已获来源及其有效性
信息、证明与依赖索引。图实现另含公开 `G,A,h`、候选宇宙、否定事实、epoch 和
前态 token。完整真实状态只交给审计者，不成为部署输入。

下表是要固定的语义职责，不表示所有接口已分别实现，也不以命名申报新算子。

| 算子职责 | 允许输入和实际写入 | 要追问的底层问题 |
|---|---|---|
| `Apply_a + Residual_a` | 原生状态与合法动作；更新实际环境及剩余契约 | 动作改变哪些事实与观察？消耗预算、扩张契约和来源失效怎样分别表示？ |
| `Need / Certify` | 可见结构、候选变换、契约；输出支持证明、需求见证或未解决状态 | 判定的是当前证书依赖，还是全部合法后续行为的需求？能否不枚举未来行为表？ |
| `Release_b` | 当前物理 b、替代支持和有效证据；联合删除 b、绑定替代证明并更新索引 | 删除与证明更新何时必须一起提交？替代支持又被删除时是否仍成立？ |
| `Rebind / Reprove` | 当前合法支持及证明；写入新证书和索引 | 换证明是否足够？证明语言的限制怎样与真正信息不足区分？ |
| `Acquire_q` | 明确来源、实体、版本、权限及请求；写入获取记录和状态相关事实 | 取得一条事实后，哪些其他查询变为不必做？拒绝、过期和未知如何返回？ |
| `Materialize / Recompute` | 合法事实或可执行重算程序及输入；写入原生可用组件 | 重建的是原内容还是行为替代？局部输入是否足够，输出是否真能用于后续操作？ |

`Retain_b` 是保留物理支持的可行选择，同样承担存储及生命周期成本。`Drop_b`
只是写操作，不自带行为正确性。`Release_b` 才承担安全省略的构造义务；它可以
编译成多个内部步骤，但只发布检查通过的完整维护状态。这里的原子性是提交
正确状态的语义要求，不是已经实现的并发事务机制。

算子失败至少分成三类：违反前提（非法动作、过期来源等）；在规定证明语言或
程序搜索范围内未找到构造；存在同一允许信息视图、却要求不同目标行为的状态。
只有最后一类提供相应的信息不足见证。不能把搜索失败自动判为不可修复。

## 4. 对现有 Need 的准确追问

在继承的 DAG、完整可达性观察及 base-edge 删除契约中，物理支持 P 不含 b 时，

\[
\mathsf{Need}_{G,A,h}(b\mid P)
=\mathbf 1\{\lambda_A^{G\cup P}(b)\le h\}.
\]

可删边容量为 1，受保护边和持久支持的容量取大于 h 的值。成功的支持路径证明
安全省略；cut 给出允许删除后该连接可能成为行为区分的见证。真实 b 是否存在、
是否能够查询，以及是否要求保留其来源身份，仍是另外的输入义务。

这个判据已有实现与范围，不能把经典 cut 或 max-flow 重命名为新理论。下一步
要回答的是：

- **增量更新**：原生动作或支持变换之后，哪些 Need 结论必须重新检查？能否
  计算足够且有明确保守程度的受影响区域，而非扫描整个候选集？
- **联合释放**：分别安全的 `Release_b` 和 `Release_c`，何时能共同执行？
  替代证明是否相互依赖，怎样给出合法次序或直接报告联合缺口？
- **证明选择**：同一行为保证有不同支持时，怎样构造可维护的证明，而非仅
  发现当前一份证明断了？依赖索引本身不能回答这件事。
- **取证反馈**：合法取得支持后，怎样直接更新其他候选的需求与实际构造？
  新增支持引起的需求变化应由结构证书解释，而非事后答案标签。

在现有契约内消费合法删除预算，旧充分表示继续充分。旧安全省略不能突然变成
必须补取的信息；更多原来保留的支持却可能变得冗余。要研究信息重新必需，须
明确引入契约扩张、来源版本变动等事件，并重新证明其接口，不能混进旧定理。

## 5. 六个决定研究能否升格的问题

**第一问：需求能否从原生算子的结构推导？** 明确组件粒度、动作读写及行为
语义。给出一个真实可执行的需求构造器；完整未来行为表只是审计规格。如果
调用原生程序作探测，权限、调用和结果取得过程都要计成本。

**第二问：构造器究竟输出什么？** 至少要把可检查的替代支持、确实尚未满足的
行为义务和可执行维护程序区分开。一般情况下可能有多套可行支持；不预设唯一
“必要组件集合”，也不把联合省略的需求写成单组件需求的并集。

**第三问：局部化什么时候成立？** 为算子给出受影响范围、安全复用条件和
复杂度边界；失败时给出反例或保守回退。单份 Γ 的依赖闭包只是一个基线，
它不等于所有可能支持的语义影响范围。

**第四问：哪些操作必须联合构造？** 固定 `Release / Rebind / Acquire /
Recompute` 的可执行次序、前提如何传递及失败如何处理。只说“操作不交换”不够；
要说明次序造成什么具体行为、可行性或成本差异，并给出构造或下界。

**第五问：独立增量在哪里？** 把候选结论与成熟依赖维护、证明复用、条件取证
和动态结构维护逐项比较。现有通用 DAG 对照继续作为强基线。如果它已能给出
同样的证书与程序，就收窄主张，继续寻找结构障碍，不以新名称保住新颖性。

**第六问：在共同原生任务上兑现什么？** 使用方法无关的支持干预，检验算子
预测的义务变化、替代与恢复；再比较实际任务行为、来源调用、重算和完整存储。
现象、理论与方法证据分别报告，图上的成立范围不自动转成 BFCL 的新结果。

## 6. 与当前代码的对应和缺口

当前 [joint_certificate_maintenance_v1.py](../experiments/oacr_theory/joint_certificate_maintenance_v1.py)
中，`counted_flow` 实现限定图模型的 Need/支持证明；`canonicalize` 按固定结构
次序选择保留边，并产生被释放边的证明；`update` 组合剩余契约、旧证书运输、
物理删减和证明绑定；`check_dag` 检查联合状态。它们不是一般载体的通用 API。

这份代码仍扫描旧物理 additions，运输全部旧证明，并执行全状态检查。当前
dependency-DAG 复用既没有新增独有增量算法，也没有建立无需全扫描的局部化界。
`update` 不接收来源接口，所以它尚未实现契约扩张后的补取或来源生命周期更新。
`Recompute` 也没有因换证明而自动获得可执行实现。

因此，本轮下一步要固定的最小接口是：

`允许视图 + 原生事件 + 候选支持变换 -> 需求/替代证书 -> 合法联合程序 -> 原生执行`

这里每个箭头都要有实际程序或清楚标注的待实现义务。完整成本决定在这些可行
程序中选择哪一个；成本函数不能替代前面的需求推导与正确构造。

2. 从一对具体的“原生事件 + 支持变换”出发，构造需求/替代证书与联合程序，
   检查局部化和次序性质，并主动找反例。
3. 固定协议和强对照后再运行有界开发检查；证据足够时才扩大共同原生任务。
