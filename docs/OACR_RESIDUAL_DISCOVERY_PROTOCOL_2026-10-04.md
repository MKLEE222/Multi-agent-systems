# OACR Residual-Discovery Protocol — let the native failures choose the next object

Date: 2026-10-04

Status: **FROZEN DEVELOPMENT PROTOCOL — no new core abstraction is authorized before a residual survives this screen.**

## 0. Why this protocol exists

The Support-Lifecycle candidate is retired as an independent core after direct coverage by ATMS,
SBFE, LPCFS, planning, provenance, materialized-view maintenance and runtime-monitoring lines.
The earlier BFCL read-view, exact-effect transport and ordinary maintenance candidates likewise
did not establish a residual advantage against correct classical controls.

The next object must therefore be induced by a repeated native residual, not selected in advance.

This protocol does **not** claim novelty. Its purpose is to make it difficult to manufacture novelty
by renaming a classical mechanism or by selecting a task after observing a favorable outcome.

## 1. Discovery question

For a fixed strong actor on native tasks, after preserving all legal information and giving classical
controls the same legal inputs, what recurrent failure or avoidable cost remains?

A residual is promotable only if all four statements are true:

1. it occurs naturally under the unchanged native task/evaluator;
2. it recurs across independent development tasks, not only a hand-built fixture;
3. the best implementable classical control tested on the same inputs does not eliminate it under
   the same correctness/completion guarantee; and
4. the residual exposes a concrete algorithmic object: a wider tractable structure, a new computable
   construction, or a same-guarantee complexity/cost improvement.

If any statement fails, classify the case and do not create a new core method around it.

## 2. Data and evaluation boundary

- AppWorld/ACE **train only** is development evidence.
- AppWorld test/test_normal is not inspected per example for design.
- The existing frozen 512-unit OACR evaluation bank remains sealed.
- Protected AppWorld task text, databases and derived full trajectories remain local under the
  benchmark distribution terms. Repository evidence is limited to public code, hashes, aggregate
  counts, non-sensitive summaries and reproducible harness code.
- A denied protected-trajectory upload is treated as the correct governance outcome, not as missing
  evidence to be bypassed.

## 3. Actor boundary

Use the same native actor interface already validated by the subagent-native train smoke:

- unchanged pinned AppWorld environment/evaluator;
- public task input and author-rendered generator context;
- initial playbook fixed before the run;
- actor receives only its own legal native receipts;
- no ground-truth API list, reference actions, private database state or post-task evaluator report
  is returned online;
- no task replacement or score-conditioned retry;
- fixed execute/time budgets declared before outcomes.

The previous 3/3 success on one scenario family is retained only as an execution-path feasibility
result. It is not evidence for or against the next mechanism.

## 4. Development sampling

The next discovery batch must be selected **before outcomes** from the unchanged train manifest.

Preferred first batch: 24 tasks stratified across distinct scenario/generator families when the public
manifest metadata permits this without reading protected gold. If family metadata is unavailable
without protected content, use a deterministic hash ordering and take a fixed prefix large enough to
avoid the previous single-scenario concentration.

Before execution, freeze:

- source revision and environment version;
- task hashes / non-sensitive family identifiers;
- actor prompt/playbook hashes;
- model/backend identity if exposed;
- actor and native-operation budgets;
- evaluator revision;
- logging schema.

Do not resample because the actor succeeds too often or because a desired failure type does not appear.

## 5. What is logged

For every task, independently of success:

### Native outcome
- task success / unchanged native tests;
- termination reason;
- native API calls;
- code-execution count;
- native execution errors and rejected calls.

### Information/cost
- visible receipt bytes;
- model-call count/tokens/cost when exposed;
- wall-clock actor time;
- maintenance/query costs for any control added later.

### Failure attribution
Classify each failure or large-cost episode into evidence-backed categories, at minimum:

1. ordinary actor reasoning/planning error;
2. missing public semantic coverage / implementation bug;
3. classical state or dependency maintenance gap;
4. observation insufficiency requiring legal reacquisition;
5. consumed/revoked permission or genuinely false guard;
6. binding / rebinding ambiguity;
7. cross-application or cross-object effect coupling;
8. evaluator/API/task-spec inconsistency;
9. unresolved.

A case may have multiple labels, but every label must cite the concrete native event or source rule
that supports it. "Memory failure" is not an admissible terminal label.

## 6. Classical-control-first rule

For every recurring residual, implement the strongest reasonable classical control **before** an
OACR-specific candidate.

Depending on the residual, controls may include:

- full legal history / exact replay;
- correct entity/version/dependency maintenance;
- ATMS-style alternative support tracking;
- SBFE/contingent adaptive acquisition;
- LPCFS-style proof/authorization state;
- materialized-view incremental maintenance/recompute;
- standard belief-state / finite-state planning;
- ordinary program-analysis or contract-inference machinery.

Controls receive the same legal observations and may use mature indexing/caching. Charge their
initialization, retained state, query/update work and reacquisition. Do not make the classical arm
artificially stateless or forbid a standard optimization available to it.

## 7. Promotion gate for a new candidate

A new core candidate may be proposed only after a residual satisfies:

### R1 — recurrence
At least 3 independent development tasks and at least 2 scenario/generator families exhibit the same
mechanistic residual, unless a stronger formal counterexample establishes the structural gap.

### R2 — native relevance
The residual changes unchanged native task completion/correctness or creates a measurable unavoidable
cost under the completion constraint. Synthetic fixture-only differences do not pass.

### R3 — classical survival
A frozen, implementable strong classical control still leaves the residual, or matches correctness only
with a demonstrably larger resource cost that is part of the registered objective.

### R4 — attributable object
The candidate's increment can be stated without OACR branding as one of:

- a strictly broader tractable input/interaction class;
- a new computable construction not already supplied by the direct neighbor;
- a same-guarantee asymptotic/parameterized or empirically material cost bound;
- a native-task capability unavailable to the control under the same legal information.

### R5 — falsifier
Before candidate execution, state a result that would retire the candidate. "No significant improvement"
is insufficient if the claimed contribution is structural.

If R1-R5 do not all hold, retain the case as a boundary, engineering adaptation or classical baseline.

## 8. Forbidden rescue moves

- Do not invent a new representation before observing a surviving residual.
- Do not weaken the baseline because it uses a classical mechanism that resembles ours.
- Do not change the native evaluator to reward a locally computed receipt that the official task does
  not recognize.
- Do not add hidden state, evaluator labels or protected gold to the constructor.
- Do not turn a one-scenario success/failure into a cross-system mechanism claim.
- Do not use a hand-crafted fixture as the sole reason to select the next core.
- Do not treat exponential generic reference algorithms as proof that a proposed heuristic is novel.
- Do not tune on sealed evaluation data.

## 9. Decision outcomes

After the discovery batch, the allowed conclusions are:

**A. No residual survives.**
The strong actor + classical controls explain the observed gaps. Stop searching in this carrier.

**B. Residual exists but is engineering-specific.**
Fix or report it; do not promote a core method.

**C. Recurrent residual survives classical controls.**
Only now open a candidate-construction branch and perform direct prior-art review on that exact object.

**D. Strong actor already succeeds with acceptable cost.**
Do not manufacture a repair problem. Move to another naturally relevant development carrier or narrow
the paper to already established contributions.
