# 24-task residual-discovery：冷审与执行门槛

日期：2026-10-04。审查对象：用户协议 commit
`9276445530198098e986f72b822843a7bb3bec9f` 的
`docs/OACR_RESIDUAL_DISCOVERY_PROTOCOL_2026-10-04.md`，以及公开旧桥
`experiments/oacr_moe/subagent_actor/{native_actor_bridge.py,actor_client.py,export_results.py,freeze.json}`。

本审查不读取 task 内容、private/gold、数据库、完整轨迹或冻结 512-unit bank，不启动
模型或原生环境。旧三项的 task/family 哈希仅从已公开 freeze 读取。它是协议与
实现一致性审查，不是结果归因或现象确认。

## 结论与范围

24 项 discovery 的设计可用于开发诊断；不能用旧 smoke 桥不经修改直接执行。
旧桥缺少 actor 总时限，异常请求会漏记 step，旧 exporter 也会排除未正常 finish 或
未评分的尝试。下列门槛须在任何 actor 取得 task prompt 前落实并冻结。

本次附加门槛比用户协议 R1 的例外更严格：不采用 formal-counterexample 豁免；
晋级仍要求至少 3 个 development tasks、至少 2 个 families，且实跑 R3 control。
这是本批的约束，不将用户原协议的例外改写为已不存在。

## 1. 选择独立性与统计单位

controller 报告 manifest 有 90 task IDs、30 family IDs；排除旧 3 instance hashes 后，
按原 manifest 顺序，取每个 family 的第一个剩余 task，取前 24 distinct families。
预定 manifest 索引为 `3,6,9,...,72`。这里的数量和索引来自 controller 的仅元信息核对；
本审查未重新读取任务或数据。旧三个 task 的 family hash 相同，已公开 smoke 只代表
一个 family 的三个 variants。

应把选择写成可机械核对的单一路径：固定 manifest/source 哈希；固定旧三项排除哈希；
固定 family 提取规则；保持 manifest 原顺序；每 family 只保留第一个合格 ID；
前缀不足 24 families 时在打开任务前失败，不改用 outcomes 或 difficulty 选样。
冻结完整 24 行 task hash、family hash、原 manifest index 及排除原因。

每 task 一个 fresh world、一个 cold `fork_turns="none"` actor，仅接收固定接口说明及自己的
合法输入/回执。共享模型来源、初始 playbook 和作者示范意味着它们并非 24 个随机独立模型，
也不是未曝光 benchmark 的确认样本。不同 family 是本批的分组单位；一项任务中的
多次错误、多个 native tests 或多次 API calls 都不能增加 recurrence 分母。
因为本批每 family 仅一项，达到 3-task recurrence 实际需要至少 3 families。

## 2. 模型可比性与成本表述

`inherited ChatGPT subagent backend` 是可记录的调用配置，不足以核实具体版本、seed、
token、计费或整个批次的后端同质性。记录已暴露的 backend 元信息及实际启动时间；
未知字段明确为 unknown。不能由“继承当前模型”推出与 DeepSeek-V3.1、原 ACE 或先前
三项完全同模型，也不能据此宣称完整公平的模型成本比较。

模型使用非零。`external_provider_model_calls=0` 只描述没有经外部 provider API 调用，
不是零次模型调用、零 token 或零美元。API calls、execute requests、receipt bytes 和
actor wall time 分别展示，不折合价格，不用工具调用数估算模型调用数。

本批执行注册将 receipt flag 明确定为原生生成 bytes，并将实际可见量另记 unknown。
预注册高成本 flags 为任一：native requester records >=100、execute requests >=20、原生生成
receipt bytes >=100000、actor elapsed >=600s。它们是筛选开发 episodes 的阈值；不是“不可避免
成本”、性能劣势或 R3 通过证明。成功且被 flag 的任务保留为成功；高成本不会触发换样。
未暴露的模型成本不可被省略后当作 total-cost 等价。

## 3. 旧桥的确定缺口与计数修正

| 公开实现位置 | 确定问题 | 新实现必须满足 |
| --- | --- | --- |
| `serve()` 的无请求轮询 | 没有 actor 总时限；可永久等待 | 不依赖 actor 自觉 finish 的 1200s 真时钟截止 |
| `execute_requests += 1` 后 `ast.parse(code)` | 解析或其它异常跳出时，计了请求却没有 execute step | 每个预算内 execute 请求均在 finally 产生 ledger 行；保留错误类型、是否实际执行及可见回执 |
| 旧 exporter `len(calls)==execute_requests==native_interactions` | 桥拒绝、parse error 与 native interaction 本来就不同 | requests、native executions/interactions、API calls 分开定义，按分类恒等核对 |
| 旧 exporter 要求末事件为 finish、grade evaluated | 超时、启动/环境/评分错误会让整批导出中断 | 固定 24 行；非正常终止/未评分也是合法结果状态，不能删行 |
| `receipt.startswith("Execution failed")` | 仅是一种文本口径，未必覆盖桥/解析/传输/环境错误 | 单独记录错误层级，不把桥错误全部称 native error |
| client 的 60s response timeout | 是一次 transport 等待，不是 actor wall deadline；超时后请求是否执行不明 | request ID 去重、终态检查，超时不自动重送 mutating execute |

冻结 logging schema 至少分别定义：预算消耗的 execute request、拒绝、解析错误、进入
`world.execute`、native environment interaction、native requester API record、native receipt、
transport/error response、finish、deadline termination、evaluator invocation。计数未知时
写 unknown 及证据缺口，不猜为 0。

原生生成 receipt、bridge 生成响应、mailbox 交付文本及模型实际可见量须分开；prompt bytes 和
JSON envelope bytes 另记。拒绝/错误响应有自身 bridge byte 计数，不进入本批明确注册的
原生生成 100000-byte flag。requester 记录计数的含义按该固定作者版本说明，
不能未经核实扩称所有 attempted API calls。

另外，bridge 保存完整 receipt 不等于 actor 看见完整 receipt：client 打印之后，host
tool 的 `max_output_tokens` 仍可能截断。固定完整合法回执的交付机制，记录 native
generated bytes、client/actor delivered bytes 与 truncation status；需要分段时只允许
读取自己的合法 response，不开放其它文件。若无法核实完整交付，不宣称完整历史
已给 actor，也不把生成 bytes 标成实际可见 bytes。

所有 24 项在 task-success 分母中；startup failure、timeout、budget exhaustion、bridge
failure、environment failure 和 evaluator error 不被替换。评分器未给出可用 success 的行
记录为非成功/未完成用于 24-task 主分母，并另列 grade status，避免声称 native evaluator
已经判 false。native tests 的 totals 对未评分项保持 unknown，不补零个虚构 tests。

## 4. 1200s 截止与评分隔离

在 freeze 中明确 `actor_start` 的唯一事件和计时边界：准备世界时间、可见 actor 窗口和
评分时间分开记录；不能重复 `start` 重置截止。使用不受 AppWorld/freezegun 冻结时间
影响的 monotonic/real clock。20s 每段 native timeout 与 1200s actor 总时限独立。

轮询时检查截止不足以称 hard deadline：正在运行的 execute、native API hang、actor
transport wait 和启动异常都可能绕过该轮询。需要独立 watchdog 或等价不可绕过的进程
控制；到期停止接收新执行，阻止排队请求继续造成副作用，终止 actor，保存已完成前缀
与 deadline/termination 事件。截止后清理与评分不得给 actor 增加行动机会。若被强制
终止导致状态不能可靠保存，保留该项为 infrastructure/timeout outcome；不要假定其
可评分，也不要续跑修补它。

40 requests 的含义固定：预算内解析错误、拒绝和原生错误都消耗一次；超额请求不能
进入原生执行。控制过程必须核实 actor endpoint 终态、活动 worker 停止以及最后可见
响应，然后才进入评分阶段。每项至多尝试一次未修改的 native evaluate_task；错误
保留为 evaluator_error，不进行评分后恢复、重跑或反馈给 actor。评分调用本身应有
独立截止，不能让全批汇总永久等待。

旧 AST 禁词与 actor 使用 client 的指令只构成补充检查；共享 workspace 不是 OS 级
隔离。新报告应延续这个限制，不把少量禁词称为防任意后端/文件访问的安全证明。
审计记录任何越界尝试；host filesystem/network/再委派的禁止规则应在固定 actor
说明中明确。classical/control arm 受同样合法输入边界约束。

## 5. Freeze、诊断与 control 的顺序

第一份 freeze 必须先于任何 task prompt 暴露或 actor 启动。其内容包括本批选择规则/
24 行哈希、旧曝光排除、source/evaluator/environment 版本、prompt/playbook/actor
说明哈希、bridge/client/watchdog/exporter 实现哈希、schema、seed123、40/20s/1200s
预算、高成本阈值、分母和本批更严格 R1 门槛。拒绝旧 output/mailbox/run ID 复用。
保存 freeze commit/hash 与各生命周期事件，运行时核对实际文件与 hash。

固定顺序：freeze discovery → 每项不可换样的 actor 尝试 → 该项 endpoint 关闭后一次评分；
全部 24 项终止并完整汇总 → 离线 attribution → 对 recurrent mechanism 注册
classical control → control 实跑 → 决定是否允许候选构造。

controller 在 termination 后获得评分是开发诊断信息。诊断可使用受授权的本地证据，
但不得把 gold/private state/evaluator labels 加到 control 的在线输入。control 是单独
注册的开发实验，不是修改原 24 项的 actor 成绩。control 运行前冻结可用输入、completion
guarantee、完整成本口径、实现、任务范围及失败判据；用 fresh worlds 和单独 run IDs。
full-history/replay 应从合法历史构造，不通过参考动作轨迹或私有 DB 重建答案。

## 6. 归因和晋级判据

对每个 native failure 及每个 high-cost episode 建一条 evidence record：task/family hash、
episode/event/request index、证据来源/哈希、主要 label、伴随 labels、certainty、竞争
解释、尚缺的核验、对应 control。公开只给非敏感索引/hash/统计；事件正文和任务内容
留本地。label 使用用户协议的九类：reasoning、semantic、classical、observation、
permission、binding、crossapp、evaluator-inconsistency、unresolved。

这些 labels 不是已证明的因果机制。尤其 semantic coverage、observation 和 classical
gap 不能仅凭失败结果区分；permission 必须由真实 guard/receipt/source rule 支持，
不能把一般 PermissionError 等同一次性授权耗尽；evaluator-inconsistency 必须有具体
API/task规则与评分行为冲突证据。主要原因与伴随条件分开；用 exact receipt/replay/
counterfactual intervention 核验时记录其开发性质。

“相同 mechanistic residual”需共用同一失败条件、状态/观测结构与可证伪预测；仅都失败、
都记错 entity 或都花很多 API 不算同一机制。至少 3 distinct tasks 与至少 2 families 才
入 R1；本批因分层选择实际至少 3 families。不能把多 tests/steps 当重复任务。

unresolved 是待核事实，不是 surviving residual。R3 必须有真实可执行并实跑的强
classical control，提供同样合法观察、标准 indexing/caching/alternatives，计入 initialization、
retained state、query/update、reacquisition 等完整注册成本，并保持相同 completion/
correctness guarantee。只列算法名字、过弱 stateless baseline、指数穷举参考、理论
相似或故障归因表都不足以通过 R3。

只有 R1-R5 全过才允许新 core candidate。R4 的对象/范围/保证须具体；R5 在候选运行
前固定能退休结构主张的结果。已有 24 项可用于发现与开发 control，但不能再包装为
独立确认；后续确认需要未用于诊断/构造的合法样本和另一次冻结。

若出现未核验项，结论写“本批暂无已通过门槛的 residual，另有 N 项 unresolved”，而不写
“残差不存在”或“classical 已解释所有 failure”。若全成功且未触发已注册成本 flag，
保留强 actor 在本批的成功事实；不为新方法制造失败。
