## 2. 共同问题由自己的算子定义

论文候选问题是：**原生操作改变一个组件所需的支持后，怎样只凭当前可得且合法的
信息，维护指定后续行为，并在保留、补取和重算之间控制全成本？**

READ、PROBE、WRITE、COMPOSE、COMPUTE 对应不同义务，不能由任务准确率统一替代。
以自己的表示组件和原生动作定义可执行保留/解码族，再定义其行为目标与成本。

候选现象也从这里产生：组件的必要性取决于操作及其他组件提供的有效支持。
原生图中，一个当前被替代路径支持的 addition，可能在允许删除破坏支持时必须保留；
其他持久 addition 又可能让它在同一未来契约下仍可省略。一般依赖失效、
“当前正确但未来不充分”与操作顺序效应已有覆盖，不能只换术语宣称新现象。
需要验证的是具体支持结构的机制预测及其发生、消失边界。

形式义务保留三项：

\[
\ker(\operatorname{Enc}_C)=\ker(B_C),\qquad
B_C(\operatorname{Dec}(\operatorname{Enc}_C(x)))=B_C(x),
\]
\[
\operatorname{Update}_a(\operatorname{Enc}_C(x))
=\operatorname{Enc}_{C/a}(T_a x).
\]

前两项分别检验类别与实际解码；第三项使用剩余契约，不能每次重置动作预算。
契约扩大不是原契约的残余更新，可能需要来源补取。来源不可得时允许程序明确
返回 UNRESOLVED，不把保持安全的拒绝当作成功完成精确修复。

## 3. 已执行：有权限和预算的来源补取

协议：[available_source_repair_v1.json](../experiments/oacr_theory/available_source_repair_v1.json)。
实现：[available_source_repair_v1.py](../experiments/oacr_theory/available_source_repair_v1.py)。
结果：[OACR_AVAILABLE_SOURCE_REPAIR_RESULT_2026-10-01.json](OACR_AVAILABLE_SOURCE_REPAIR_RESULT_2026-10-01.json)。
逐配置记录另存为同名 `.cases.json.gz`，摘要记录其 SHA-256。

这轮是固定协议的小型结构接口检查，不是独立自然复制。具体状态为公开 DAG 加零或
一个未知的持久 addition；旧表示保证是同一冻结状态的正确旧编码。程序只见旧标签、
公开 G、候选 D、旧/新删除契约、来源快照与权限/预算接口。初始编码的完整来源读取
单列，之后的 repair 函数不接收隐藏 addition 或未来行为矩阵。

来源只支持单位成本的单候选 membership 查询；它强制检查权限、快照 epoch 和预算。
因此模型改变为原始 delta ID、组合查询、任意多个 additions 或来源变化时，
必须重新分析，不能直接套用本结论。

设公开 cut 编译得到两个 active 集合。对于旧 bottom 标签，需要补取的候选集合为

\[
K=\operatorname{Active}(C_{\rm new})
  \setminus\operatorname{Active}(C_{\rm old}).
\]

旧标签已显式保存某个 addition 时，当前状态身份已知，不需要来源查询；否则按固定
顺序查询 K 中获准项。一次肯定答案在单 addition 假设下确定状态；全部否定确定新
bottom。仍有未查候选且无肯定答案时返回 UNRESOLVED。来源快照不匹配时不读取它。

在 base 状态的全否定分支，每个未查的 k∈K 都是与旧表示和既有回答相容、却有不同
新行为的状态。精确的 singleton 查询算法因此最坏需要 |K| 个否定回答；本程序在
权限完整、预算足够时达到它。这是线性搜索的基本信息界，不是满足 T2 的新定理。

| 检查 | 分母 | 结果 |
|---|---:|---|
| 7 组预先固定 fixture 的状态×权限×预算×版本配置 | 1,664 | 938 EXACT，726 UNRESOLVED |
| 成功输出的原生解码 | 938 | 零不匹配 |
| 未完成输出的实际歧义 | 726 | 每项均有至少两种相容的新行为 |
| 已知状态或无新隐藏需求 | 816 | 精确完成，零来源查询 |
| 修复后不同具体世界的残余维护 | 34 | 166 个状态、156 条更新检查，零不匹配 |
| 全权限、充足预算下的 base 否定分支 | 20 | 查询数等于 |K| |
| 来源 API 的权限、版本、初始及耗尽预算强制检查 | 4 | 均拒绝违规请求 |

938/1,664 不是自然成功率，726/1,664 不是基准失败率；它们来自有意包含不可得来源
的开发笛卡尔积。不同 fixture 的重复权限集也保留在原分母，不能充当独立样本。

成本分开记录：34 次初始来源读取；54 次公共 cut 请求（40 cache hits、14 misses）；
在线补取共 636 次 membership 查询；验证器另外执行 4,558 次原生 closure。
验证器用 failure 枚举和 bitset Warshall，不向构造器返回结果。
在线程序原生 oracle 调用为零，违规/过期/超预算查询为零。
初始来源存储的物理成本未测量，是明确的外部前提；公共图、动作集、候选集和 active
元数据、查询记录与工作集合均需要存储。单次本地耗时仅供复现，不声称总体成本优势。

复现：

```bash
PYTHONDONTWRITEBYTECODE=1 python experiments/oacr_theory/available_source_repair_v1.py --out /tmp/oacr_available_source.json
```

## 4. 升级优先级与停止条件

1. **把结构结果的独立增量查清。** 围绕条件组件需求、允许修复语言及合法来源约束，
   对照 complete cores/shells、observational completeness、状态抽象与 fault-tolerant
   reachability/reduction。已有算法若完整覆盖某结果，就明确归为实现或应用；
   不继续靠扩大图枚举数量推进 T2/T5。当前 singleton 接口是执行基线。
2. **用原生载体确认机制。** 保留来源支持的 R4 图结果和组件交互结果作为基础，
   冻结当前读取、目标省略、支持失效/恢复、无关操作与 sham 对照。
   实际补取和依赖维护都计费，与完整重建、标准依赖闭包和结构专用算法比较。
   先确认同一机制，之后再判断第二载体是否检验同一规则。
3. **使学习型表示真正可维护。** GRACE 当前辅助 gate 的结果没有建立该对象。
   下一阶段须先展示原生表示干预确实改变所声明的区分和更新路径，再测任务收益。
   缓存的固定输入机制检查保留为局部结果；简单精确复用已经修复结构缺口，
   没有全成本障碍之前不把学习刷新控制器设为主线。

现象成立但标准维护已经充分解释或低成本解决时，收窄到成立的知识；机制预测失败
时修改或放弃该假设。T2/T5、独立证明审查和自然维护证据仍未关闭；旧 512 单位
评估继续封存。本次完成的是既有 OACR 核心的来源可得性执行升级，不宣称论文已强到
通过验收或保证发表。
