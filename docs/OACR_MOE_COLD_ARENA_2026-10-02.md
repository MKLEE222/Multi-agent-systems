本报告为独立开发诊断，不是新独立确认，也不改变冻结 producer、共享文档或验收门。
旧 512 单元未读、未解封。没有运行模型，没有调参或挑收益案例。

### 官方指标与代价目标的错位

原 checker 每轮比较原生实例状态，并要求该轮参考回执的每个 occurrence 出现在
累计真实执行回执中。它允许复用早先真实取得的匹配回执，但不会因为本地推出一个
新回执就把它当作已执行。因此已知内容推出首次 `wc` 输出，仍须执行原生 `wc`。
19 次可计算输出与 0 次官方认可省调用并不矛盾。

两条过滤分支此次保留全部 276 个动作，所以通过 checker 对记忆机制几乎没有
区分力。后续必须保留官方 checker，另列“本地可计算率”“实际工具调用数”，
不能给 checker 注入合成回执后继续称原官方分数。

本轮成本分列为：经典 query 84、update 939、bundle 峰值之和 87,837 bytes；
候选 query 169、update 466、bundle 92,837 bytes。候选多 5,000 bytes，且工作
原语不同，不能只截取较小 update 数宣称胜出。0 模型调用与很短历史也使该轮无法
区分真实 agent 的抽取、反思、图构造、检索、缓存与上下文成本。

还有独立的任务语义问题：base_49 用户要求重排文件后显示最后 10 行，但原生
`sort` 只返回排序字符串，不写回；参考随后 `tail` 取得原始顺序。官方通过并不
证明“排序已落盘”或最终 tail 符合该自然语言意图。此处应保留官方结果，另标任务
意图与 API/reference 的不一致，不能通过改 evaluator 给自己的方法加分。

### 信息不足的具体含义

base_0 的 `grep` 已返回带 budget analysis 的一行，却不能保证文件只有这一行。
在隐藏原内容后插入一行不含该 pattern 的 marker，先前 `grep` 不变，下一 `sort`
增加一行。这解释为何不能把 grep 匹配行当完整文件。

base_34 的 `tail(lines=1)` 返回最后一行，也不能保证文件只有一行；在该行前增加
marker，先前 tail 不变，下一 cat 改变。base_49 的 sort 保留行多重集却丢原始
行顺序；反转原文件保留 sort 回执，下一 tail 改变。这是查询信息本身的缺口，
不是词面检索遗漏，也不是未知目录类型造成的回退。

base_33 index 2：过去是 `ls()` 和 `grep(pattern='def')`，后者返回已知单行 R。
相容文件可以是 R，也可以是 `R + '\nupdate'`。新行不含 `def`，所以过去回执
完全相同；它包含 `update`，所以下一 `grep(pattern='update')` 多返回该行。
原生 grep 明确逐行作子串检查，证明不依赖“实际文件恰好只有一行”的隐藏事实。
这是第 51 个信息不足见证，未作为第二次开发运行。

这些见证只说明该契约下下一精确回执不能被唯一确定。允许合法补查后仍可取得
内容；猜测也可能碰巧预测实际世界。不应把它写成所有方法的实际正确率上界，或
把普通不可辨论证包装成新定理。相容世界族须允许上述合法内容变体；若实际输入
增加了约束，需要重新核对见证是否相容。

### 三个实现缺口

| read | 仅使用的过去可见依据 | 可确定结果 | 冻结实现为何漏掉 |
| --- | --- | --- | --- |
| base_10 index 8 `diff(notes.md, summary.txt)` | 成功 cd 到 Projects；随后成功 touch 两文件、echo summary 为 Hello；其间无导航或别的写入 | `{'diff_lines': ''}` | 早先未确认类型的 mv 触发 conservative；之后每个写入又全局失效，丢掉已创建的空 notes；且没有利用 zip 在空序列一侧的短路 |
| base_16 index 5 `wc(..., mode='l')` | 上次同文件 sort 成功，sorted_content 是非空单行；其间无写入/导航 | `{'count': 1, 'type': 'lines'}` | views 只复用相同 query 参数；没有从 sort 的完整行集合推出行数 |
| base_49 index 3 `wc(file3.txt, mode='l')` | 同文件非空 sort 回执有 20 行；其间 tail 为纯读 | `{'count': 20, 'type': 'lines'}` | 同上；已有部分视图的信息未用于不同 read |

上述行数关系只对这些已观察到的非空 sort 回执作证明，不能粗暴泛化为所有情况：
空输出可能来自零行或空行，分隔符归一化也须按源函数处理。diff 短路仍须有文件
存在和类型的依据；本例成功 touch/echo 提供该依据。不能不验 guard 就因为一个
内容为空而跳过另一文件的合法性。

在这个有限可见契约及相容世界族下，19 个已知项加这 3 项至少可覆盖 22 个；51 个
不可辨见证阻止其成为无补查的“跨全部相容世界 exact certificate”。这是逐前缀
信息诊断，不是新方法分数、完整 agent 准确率上界或独立自然现象确认。

## 3. 真正剩余的研究缺口

1. **完整闭环失败尚未观测。** 我们没有完整 ACE/AMA/AgeMem 的实际决策、失败
   轨迹与全成本；accessor 缺 witness 不填补这一义务。
2. **强经典对照尚未完整。** 当前经典实现与候选共享保守 adapter，同时漏掉部分
   query implication 和已创建局部对象的独立性。先补足类型/alias/guard/部分视图
   维护，再检验候选增量；补足这些是基线工程，不是 OCAR 新核心。
3. **候选并未有新的可冻结构造。** 当前 backward slice 不能因使用真实文件任务
   自动获得新颖性。只有与完整强系统及成熟维护竞争后，真实剩余结构或同保证联合
   成本问题才可能成为新候选。
4. **机制规律尚未确认。** 当前发生过重绑定但经典已追平；没有测到支持失效/
   恢复与 sham 的成组干预，也没有跨系统同一核心规则的证据。

因此不应再增加几个 hand-crafted alias fixture 作为新“真实任务”。这些 fixture
可以验证 adapter，但不能替代近邻原任务、全分母及实际 actor。BFCL 这批短轨迹
可保留为语义回归与旧结果诊断，不能重新标成独立确认集。

## 4. 下一轮最小高辨别力 arena

### 优先载体与运行就绪

优先核对 ACE 原生 AppWorld runner。主线程已发现 ACE 固定 tree 的 `ace-appworld`
gitlink，指向 `9f3e921…`；“根 tree 没看到 runner”不能据此当作不存在。须把完整
子模块 SHA、原生配置、AppWorld app bundle、split、评测器和模型角色实际拉齐、
运行一轮官方 train smoke 后再称运行就绪。本报告未独立复现该 runner。

选 AppWorld 的理由是 ACE 的真实竞技入口和实际数据库/答案检查，而不是预设它
会暴露特定 alias 故障。遵守禁止硬编码领域 API 的原生 agent 规则；组件只处理
各臂合法可见的调用/回执与通用元数据，由 actor 选择原生调用。不能偷看数据库、
私有 evaluator、初始/最终标签或未打印的中间内部对象。

AMA 的完整图/embedding/缺口自评/原始轨迹回查不可删减，但在 AppWorld 上新移植
必须称移植，不能冒充其作者 TextWorld/Spider2 复现。AgeMem 没有实际训练 checkpoint
时不能用独立 demo 冒充论文系统。这两个原生 carrier 可成为后续迁移，不能为凑齐
名字而挤进首个最小 arena。首轮先把一个真实强 baseline 完整跑通。

### 三条最小主臂

| 主臂 | 保留能力 | 差异定位 |
| --- | --- | --- |
| ACE native complete | 作者原生 actor/reflector/curator、playbook、允许的反馈、历史回查与缓存 | 完整强 baseline，不用 accessor 替身 |
| ACE + classical maintenance | 同一 ACE 全能力，加正确的合法可见实体/类型/版本/guard/依赖/部分视图维护；允许局部索引与缓存 | 维护适配的工程价值及成熟解法上限 |
| ACE + demand candidate | 同一 ACE 全能力、同一语义片段与 fallback，加 demand compiler；尚未升格为 OCAR 新算法 | 候选是否比成熟维护多出正确性或联合成本收益 |

独立 full-history 原生 ReAct 是有用的第四臂，只在其可直接按作者配置运行时加入；
不以它替代 ACE。经典和候选共用已验的 adapter，保留完全相同的 raw archive
能力并收费。若共享 adapter 的收益是核心实际来源，归给 adapter；不全归给候选。

### 输入和资源公平

- 同任务、相同 actor 与温度/seed 面板、工具权限、原生文档、上下文与执行限额。
  各臂可选择不同未来轨迹；不把一个参考轨迹强塞给所有 actor 后宣称闭环收益。
- 先选择作者一种明确的 offline/online/监督设置，完整保留它的训练/反馈预算。
  共同训练出的策略 playbook 冻结给三臂；task-local 状态另比较。反馈权限若不同，
  分独立协议，不能混合计分。绝不从 dev 私有评分端偷偷提供补查答案。
- 相同公开来源与经验池，经典也可使用合法语义元数据和局部优化。候选不存在
  免费稳定 ID、全局版本号、未见 writer 通知或任意无限来源补查。
- 未支持、超时、规格检查未完成、真实信息歧义分列。当前 API 调用产生部分写入
  或无法证明只读时，禁止依据旧查询回执直接抹去调用；执行原生 fallback 并计费。

### 样本与预先停止条件

建议第一轮为**开发筛查**：从官方 development task ID 用固定 source pin 与
`SHA256(pin + task_id)` 排序，取前 24 项；全集不足 24 就取全集。不读私有目标或
逐例分数选样；若公共 template/family 元数据可用，先固定模板分层配额和选择规则，
避免同模板占满。manifest 必须在运行前列实际 ID、split、同模板关联和所有限额。

每任务 3 个预定 seed；最小三臂为 216 个闭环 episode（数据不足时相应减少）。
seed 是重复而非独立任务，统计以任务/公开模板聚类。24 项只筛查较大效应，不保证
精确估计小收益，也不能因其存在就标成确认性 benchmark。旧暴露 BFCL 不混入。

运行前固定作者原限额或一个各臂一致的限额；所有重试、反思和成本进入账本。
达到固定全样本终点才做收益判决，不在出现漂亮差异时提前停止。

- runner、依赖或模型不可用：记录具体缺口，只完成 source/runtime capsule，
  不输出虚构完整方法分数。
- 任一 supposedly sound 的操作证书与原生执行不一致：记录失败和触发输入，暂停
  证书优势主张；其 safe fallback 仍可作为显式退化分支完成预定任务。
- 官方收益持平且候选联合成本被经典追平/支配：此候选收为基础工程，不继续补
  特例直到赢。此判断限于本轮开发范围，不声称全局算法不可能。
- 官方改善只由共同 adapter 解释、经典同步改善：支持适配价值，不升级候选核心。
- 样本不确定：报告不确定；不根据结果临时扩充“有机会”的任务。新的确认轮须在
  下一批结果暴露前独立固定。

独立确认用未暴露的官方可用任务 split、原规则和同一冻结构造；test 不用于调参或
机制选例。是否使用官方 test 及可见反馈权限按作者协议核实。旧 512 封存与本轮无关。

### 三种结果分别测

| 结果层 | 必须保留的量 | 判断用途 |
| --- | --- | --- |
| 官方任务结果 | 未改 evaluator 的 TGC/SGC、每 task/seed 结果、失败与空输出；完整任务分母 | 实际是否做成原任务 |
| 全部成本 | 训练/优化与初始化；actor/reflector/curator/抽取/embedding/检索调用；输入输出及缓存 tokens；真实 API/来源/环境调用；写入/重算；raw/archive/索引/图/证书/缓存 bytes；CPU、墙时及尾部；真实价格计费若可得 | 是否有联合成本收益；冷启动与摊销分列 |
| 操作与依据正确性 | 当前绑定、值、guard、效果/部分写入、依据来源；证书真/假、unsupported、ambiguity；task 意图与 API/reference 歧义 | 是否减少被声称的失效路径，而非碰巧得分 |

不把官方分数、证书正确率和成本揉成一个掩盖失败的分数。主结果用配对任务差异，
同时给净胜/净负任务、任务聚类区间和成本 Pareto 关系；调用与 tokens 总量、尾部
保留，平均值不掩盖一个方法靠大量补查救回少数任务。

### 不另造 toy 的最小机制层

先冻结上述自然闭环轨迹，从完整 baseline 的可见调用/回执中按**所有**声明操作
及支持事件提取合法 anchor；无事件的任务仍计入任务分母。以 baseline 实际操作
做 replay 下的维护/证书测量，明示这是机制辅助层，不是另一种闭环 agent 得分。

组件保留/省略、已有支持有效/自然失效/合法取证恢复，以及字节和类型匹配的 sham
分别处理；未来答案不传给 producer，恢复必须真实执行原生调用并计费。受影响与
无关操作按源码义务在结果暴露前分组。机制若不能预测失效与消失边界，候选规律
退回描述；若经典维护消除全部效果，也如实记录。原始历史可回查，不人为拿走
AMA/ACE 的强能力来制造支持“复活”。

这一层的价值在于解释原生强方法真实遇到的障碍。若自然轨迹几乎没有相应支持
失效/恢复机会，就应报告该任务不识别这条机制；不能补几个挑中的 fixture 后声称
自然发生率。当前没有足够证据承诺 AppWorld 必然提供某一种新机制。

## 5. 建议的立即推进顺序

1. 保存本诊断，将 3 个漏覆盖作为完整经典 adapter 的必要检查项；冻结 BFCL
   实现与其原结果保持原样，另版本才能修复。不要把 51 项歧义算成研究失败或新定理。
2. 核实 ACE AppWorld 子模块、角色配置和 app bundle，运行原生 smoke，建立包含
   训练/反馈与模型依赖的完整 capsule。真实阻塞项一项项确认，不能从根 tree 的
   文件列表推断 runner 或所有模型能力不存在。
3. 在看新逐例结果之前冻结三臂、合法输入、经典语义覆盖、任务 ID/seed/限额、
   原官方 evaluator 和全成本账本。尚无独立新内核，就诚实使用当前未升格 candidate。
4. 执行真实闭环开发筛查，以观察到且经典无法完整追平的剩余缺口提出下一候选；
   再冻结独立确认。由任务推动理论，避免再用一个自己设计的母问题获得循环胜利。

本报告不改旧贡献判决或 Acceptance Gate；它提供一个可执行的差距定位：**完整强
方法原生闭环与成熟语义维护尚未一起跑过，当前候选的新核心仍为空。**
